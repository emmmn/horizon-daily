### [vLLM 推出分层 KV 缓存卸载](https://vllm.ai/blog/2026-09-10-tiered-kv-offloading) ⭐️ 7.0/10

vLLM 自 v0.22 起提供分层 KV 缓存卸载（tiered KV cache offloading），将原本因加速器内存（如 GPU HBM）耗尽而被逐出的 KV 数据保留在主机内存、存储和远程对等节点中，从而避免重新计算、降低延迟并提升集群的有效服务容量。其核心设计是所有 KV 数据都经由主机内存（CPU DRAM）流转：卸载时先从加速器异步 DMA 到主机并立即释放加速器内存，再级联到文件系统、S3 兼容对象存储或远程对等节点等二级层；重载时二级层先提升到主机内存，再加载到加速器，实现即时分配。主机层是真正的 LRU/ARC 缓存而非暂存缓冲区，二级层按配置顺序查询，未命中时调度器收到 RETRY 并在下一周期重试，同一请求的不同 chunk 可由不同层服务。主机侧采用与配置无关的规范化内存布局，使不同加速器类型、注意力后端（FlashAttention、FlashInfer、Triton）和并行配置（如 TP=2 与 TP=4）的节点可直接共享 KV 数据而无需重映射。该框架还支持 P2P 跨节点共享（ZMQ 协调、NIXL 上的 RDMA 传输），用于预填充/解码分离和负载均衡，并兼容滑动窗口、MLA、Mamba 等混合架构（如 DeepSeek V4、GLM 5.3、Nemotron 3），同时通过 /metrics 暴露主机缓存利用率、传输吞吐、各层延迟与命中率等 Prometheus 指标。

rss · vLLM Blog · 9月10日 00:00

**「背景」** 长上下文模型和多轮对话会产生庞大的 KV 缓存，当 GPU HBM 等加速器内存被填满时，vLLM 会逐出已计算的 KV 数据，下次需要时只能从头重算，造成额外计算和延迟。分层卸载的思路是把被逐出的 KV 数据保留在更低成本的存储层级中，需要时再加载回来，而不是重新计算。由于 KV 数据可跨节点共享，这一机制也为水平扩展缓存、预热新实例以及分离式服务提供了基础。

**「影响」** 对运行长上下文或多轮对话负载的 vLLM 部署而言，该功能可减少重复预填充计算、降低延迟并提升集群有效服务容量，同时让不同硬件与并行配置的节点直接共享 KV 数据。P2P 层将多个小的逐 GPU 传输合并为更少、更大的 RDMA 操作，可显著改善网络吞吐，并使预填充/解码分离与负载均衡更易实现。

### [vLLM 混合 HiSparse 卸载让 GLM 5.3 单节点跑满 1M 上下文](https://vllm.ai/blog/2026-09-08-glm53-part1-hybrid-sparse-offloading) ⭐️ 7.0/10

vLLM 团队发布 GLM 5.3 优化系列第一篇，介绍 Hybrid HiSparse 卸载机制：在单台 8× H200 节点上，GLM 5.3 首次可以运行完整的 100 万 token 上下文，并在各上下文长度下实现显著更高的并发。该方案针对稀疏 MLA KV cache，利用 indexer 只关注 top-K token 的特性，将未被选中的 KV 卸载到 CPU，仅保留 indexer KV 在 GPU；同时只要显存充足就继续把 KV 留在 GPU，仅在 KV cache 承压时才逐页放弃驻留。热缓冲区与常驻页共享同一 HMA 池和 KV-cache 张量，因此对稀疏 MLA kernel 而言与普通页无异，解码路径无需等待 CPU 决策，仍可被 CUDA graph 捕获。基准测试使用 OpenHands 多轮 agentic 负载（13 轮对话、首轮 74,160 token、后续 753 token、固定 220 token 输出），TP8、MTP3、FP8 KV cache、142K 准入上限、max\_num\_batched\_tokens=32768、max\_num\_seqs=256、gpu\_memory\_utilization=0.92；基线使用 512 GiB 卸载池，Hybrid HiSparse 将同一主机预算拆为 384 GiB HiSparse 池与 128 GiB 卸载池。该功能计划在 vLLM v0.30 中广泛提供。

rss · vLLM Blog · 9月8日 00:00

**「背景」** Agentic 工作负载的特点是大量并发请求，每个请求上下文很长且持续增长；由于 GPU block pool 固定，KV cache 最终会耗尽空间。此前主要有两种应对方式：抢占会丢弃请求的 KV cache 并稍后重新 prefill，导致每次驱逐都要重付完整 TTFT；卸载把块移到主机内存，但稠密注意力要求所有 token 常驻 GPU，并发数仍受显存限制。稀疏 MLA 的 indexer 只选择 top-K token 进行注意力计算，HiSparse 正是利用这一行为把其余 KV 放到 CPU，而 GLM 5.3 的 IndexShare 使每四个稀疏 MLA 层只有一个 indexer 层，进一步压缩了 GPU 侧开销。

**「影响」** 对在单台 8× H200 节点上部署 GLM 5.3 长上下文 agentic 服务的团队而言，Hybrid HiSparse 使 1M 上下文从不可行变为可行，并在相同 HBM 下提升并发；该功能计划随 vLLM v0.30 广泛提供，但具体收益取决于工作负载、并行度、热缓冲区与主机池配置。

### [Brown 博客系统梳理 async/await 的九维设计空间](https://cel.cs.brown.edu/blog/design-space-async-await/) ⭐️ 8.0/10

布朗大学（Brown University）的一篇博客文章对 async/await 的设计空间进行了系统化梳理，将其拆解为九个设计维度，并跨多种编程语言进行比较。文章强调从语义出发而非表面语法来理解异步机制，涵盖并发语义、运行时实现选择以及“函数颜色”（function color）等权衡。该文在 Hacker News 上引发了关于并发语义与函数颜色问题的深入讨论。

hackernews · wcrichton · 9月9日 13:59 · [社区讨论](https://news.ycombinator.com/item?id=49626718)

**「背景」** async/await 已成为众多编程语言处理异步计算的主流语法，但不同语言在实现语义上差异很大。布朗大学的研究者提出一个包含九个维度的设计空间，覆盖异步计算从调用到完成的整个生命周期，例如语言在调用异步函数时给出哪些精确保证。相关论文《A Design Space Exploration of Async / Await》对这一框架进行了系统阐述。

**「影响」** 对于正在设计或选用异步运行时的语言设计者和后端工程师而言，该文提供的九维框架可作为系统化决策清单，帮助识别函数着色、同步/异步互调限制等取舍；但文中维度的影响尚未被完全理解，相关结论仍需结合具体语言实现验证。

**「社区讨论」** 评论者普遍认为这种语义优先的跨语言比较分析极具价值，有人指出理解各语言在并发、类型、求值策略等方面的权衡比学习具体语言课程更能提升编程能力。多位评论者强调 async/await 看似简单实则设计选择众多且影响深远，其中一位正在设计新语言（Zena）的开发者表示该九维框架帮助其厘清了决策点。也有评论者指出 JavaScript 中 async 函数可调用同步函数并使用其结果，但同步函数无法以任何方式使用异步函数的结果，且将已有调用方的同步函数改为异步函数往往会导致调用方出错，这一问题会沿调用树向上蔓延。
